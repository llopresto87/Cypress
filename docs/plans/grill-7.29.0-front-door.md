## 2. Shared Understanding
A first reader of the seed's README judges the project "too complex" because the README uses standard words for non-standard things without saying so, and asks the reader to learn the vocabulary before telling them what the project is, what it does to their repository, what it costs, and what it actually enforces. The clearest case: once installed, an "agent" is a role file the host can run in its own context window with a restricted tool list; otherwise it behaves like a skill file, which is read into whichever context is working. The README presents "a 20-agent team".

A measured baseline confirms it (detective evidence, not a gate): three fresh model sessions given only the README's first screen (lines 1–413) answered seven reader questions; the median session answered 1 of 7 fully correctly, and every reader listed the seed's source tree as "what installing adds". Six of their errors trace to README lines that are stale or overclaim (§12 of the harvest proposal; mismatch register M-rows).

Success: the README answers the first reader's five questions (what it is, who it is for, what installing does to the repository, what it costs, how to try it) on its first screen and in that order, before any coined term is needed; every borrowed term sits beside its field meaning, where the seed departs from it, and the file that implements it; every coined term is defined once; every enforcement claim traces to an artifact and carries its ADR-0003 class; every gate that pinned a README fact still pins that fact where it now lives, at the same strength or stricter.

Out of scope: any change to mechanism (hooks, installer, linters' semantics beyond the new SPEC-0004 checks and the per-file prose-lint split the steward approved); host-release facts that contradict seed method nodes (hooks reaching subagents, the spawn tool's name, spawn-depth limits, agent-directory registration) — recorded in the mismatch register and routed as a separate change; renaming any concept.

## 3. User Goal
- Primary user: a developer evaluating the seed from its README, who has never seen it and uses (or is considering) an AI coding agent
- Primary outcome: within the first screen, knows what the seed is, whether it is for them, which files an install writes and how replaced files are kept, what it costs per session and how that figure was obtained, and how to try it
- Job to be done: decide whether to install the seed, and understand what they would be agreeing to, without learning project vocabulary first
- Acceptance criteria (link to spec §9): [SPEC-0004 §9](../specs/SPEC-0004-front-door.md) — to be authored by product in this pass
- Non-goals: making the project look simpler than it is (the limits section stays); removing cost figures; teaching the method (the manual and references do that); changing what the seed does

## 4. Operating Constraints
- Runtime constraints: checks run inside `tests/run.sh` under the existing step budget; stdlib Python 3 and bash 3.2-compatible shell only
- Security constraints: no secret, credential, host, user path or plant identifier in any seed file (harvest G1/G2); no production data in fixtures
- Privacy constraints: the donor plant is never named in any seed-committed file; plant identity lives only in the steward's ratification proposal
- Data constraints: none — documentation and lint code only
- Cost constraints: no widened budget, ceiling or ratchet (harvest G11); new ratchets start at their strict value; the kernel is not touched, so eager bytes do not move
- Latency constraints: new seed-lint checks must not measurably slow `tests/run.sh` (text scans over a handful of files)
- Compliance constraints: none
- Maintenance constraints: every figure that can drift is stated only where a lint check pins it; definitions are written against the mechanism, not a version; one home per fact, enforced by DEFINITION_HAS_ONE_HOME; every moved fact takes its check with it in the same commit; ADR bodies are never rewritten (corrections are dated amendments)

## 8. Architecture Plan
- System boundary: seed-side only. `install.sh` places none of the front-door files (`README.md`, `DOCUMENTATION.md`, `documentation/*.md`, `INSTALL.md`, `integrations/*/README.md`): its `place_tree` calls name `protocols`, `core/method`, `agents` and `templates` (`install.sh:815-827`), and `README.md` appears there only in skip patterns (`:758`, `:1393`, `:1498`). Nothing here reaches a project; a definition a project session needs keeps its home in the machinery node that ships. The boundaries crossed are prose (front-door files), the seed's own lint (`tests/seed-lint.py`) and the gate's registry and runner (`tools/gate-registry.py`, `tests/run.sh`).
- Main components:
  1. Front-door prose: README in nine sections; glossary at `DOCUMENTATION.md` §15; enforcement table at §17; reference openers; one sentence in the matrix class table.
  2. Front-door parser, inside `tests/seed-lint.py`: body text, units, inline links, explicit anchors, README sections, glossary entries, enforcement rows, tables (SPEC-0004 §6).
  3. Front-door checks, inside `tests/seed-lint.py`: one `check_fd_<slug>` per seed-lint contract, called by one dispatcher after the existing checks.
  4. Pending ledger: `FRONT_DOOR_PENDING` in `tests/seed-lint.py`, mirrored in `tests/ratchets.json` and mapped in `tools/ratchet-lint.py`.
  5. Planted cases: `case_fd_*` in `tests/test-seed-lint.sh` over the fixture `tests/fixtures/front-door/`.
  6. Gate registry: per-file prose steps, and the seed-lint entry's false-green note.
- Interfaces:
  - `fd_fail(slug, path, line, message)`: the one reporting path; prints the finding and calls `fail()`, or records it for the slug's PENDING line.
  - `fd_guard(slug)` (added 2026-09-24): a context manager around each call, `with fd_guard("<SLUG>"): check_fd_<name>()`, one call per line so the coverage binder sees it live. The justification in `templates/prompts/graph-session-bootstrap.md:4-5`
("hooks do not reach subagents, so the brief is the only enforcement that
crosses the boundary") and `templates/prompts/handback-payload.md:6-7` ("where
hooks do not reach, so this block is the only reliable carrier") is false as
stated. The doctrine it defends still holds, for a narrower and honest reason:

- **No hook the seed installs carries the graph discipline or the routing
  context into a worker's turn.** The route hook is prompt-scoped, and its
  firing for a subagent's turn is not recorded. The tool hooks that do fire
  inside a worker guard tool calls and carry no routing context. So the brief
  is still the only carrier of both across the spawn boundary, and embedding
  the bootstrap verbatim stays mandatory.
- **No hook the seed installs reads a worker's result.** The seed wires no
  `SubagentStop` hook, and ADR-0003 keeps the top-session `Stop` hook unwired
  on purpose. So the handback block is still the only reliable carrier of
  `produced_by` back to the caller.
- **What changes:** the brief is no longer "the only enforcement that
  crosses." The pre-Bash guard also crosses: it is a tool hook, and it fires on
  a worker's Bash calls. Sentences that call the brief the only enforcement
  become "the only carrier of the discipline."

Wording for the two templates (the implementer may trim it but may not
strengthen it). Bootstrap `:4-5`: "(no hook the seed installs carries this
discipline or the routing context into a worker's turn; tool hooks such as the

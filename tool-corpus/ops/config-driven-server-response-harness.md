# Tool: config-driven-server-response-harness

> Project-agnostic, durable capability notes, folded into the seed by the
> harvest protocol. This page is a **BLUEPRINT**: the argument, the staging
> sequence, and the declared blind spot are portable; the config-rewrite table
> that makes a real configuration run detached is binary-specific and is written
> per server.

## 0. Identity

- **Category:** ops
- **Name:** config-driven-server-response-harness
- **Language / runtime:** any (a script driver, the server binary itself, and a
  protocol client)
- **Stability:** **blueprint only** — no portable implementation. The rewrite
  rules that turn a production configuration into one that runs in a scratch
  directory without daemonizing are specific to each server binary, which is
  exactly why this is a blueprint and not a script.

## 1. What it does

Measures what a config-driven server binary **actually emits over the wire** for
a chosen route and header matrix — without a daemon, without live upstreams, and
without touching the running system.

It exists because the usual alternative is **static analysis of the
configuration**: reading the config files and reasoning about what the server
would do. That reasoning is a reimplementation of the server's own directive
resolution — inheritance between scopes, ordering rules, which directives replace
rather than merge, which are dropped in an error path — and it is wrong in
exactly the places where the configuration is subtle. The binary already knows.
Ask it.

Optionally, it does the same against **two revisions** of the configuration and
diffs the emitted responses, which turns "did this change alter what clients
see?" into a mechanical comparison rather than a review opinion.

## 2. Interface & invocation

```sh
response-harness \
  --config <the real, committed configuration tree> \
  [--config-b <a second revision, to diff against>] \
  --route <path> [--route <path> ...] \
  --header-matrix <the set of request header combinations to send> \
  [--port <scratch listen port>]
```

- **Inputs:** the real configuration tree as committed; the routes to probe; the
  header matrix; optionally a second configuration revision.
- **Outputs:** per route and header combination, the **status line and full
  response headers as emitted**, and a verdict per asserted rule; in diff mode, a
  per-response difference between the two revisions.
- **Exit codes:** non-zero on any asserted rule that is not present in the
  emitted response, on a syntax-check failure, or on a render failure.
- **Preconditions:** the server binary is available locally; it has a
  **syntax-check mode**; it can be told to run in the foreground with a
  caller-chosen prefix, log destination, and listen address.

## 3. Approach / algorithm

Four steps, in order. Each one exists to remove a specific way the measurement
could be a fiction.

### 1. Render the real, committed configuration into a scratch environment

Copy the **committed** configuration — not a hand-written approximation of it —
into a throwaway directory, and apply a **rewrite table** so it can run there: a
caller-chosen listen address and port, foreground execution rather than
daemonizing, scratch paths for logs, temporary state, and process files, and
removal of directives that require privileges or system integration the harness
does not have.

Keep the rewrite table **small, explicit, and enumerated**, and print it. Every
rewritten directive is a difference between what is measured and what runs in
production, so the list of them is part of the result, not an implementation
detail. If the table ever needs to touch a directive that participates in the
property under test, the harness is no longer measuring that property.

### 2. Validate with the binary's own syntax-check mode

Before starting anything, run the server's own configuration check against the
rendered tree. This catches rewrite mistakes immediately and, more importantly,
guarantees that what follows is a configuration the **binary** accepts — not one
the harness believes is fine.

### 3. Sever every upstream to a dead local port

Point every backend, proxy target, and upstream at a local port with nothing
listening. The server then answers every proxied route with **its own error
response**, generated by its own configuration, with no dependency on any service
being up.

### 4. Measure the emitted response

Send each route × header-matrix combination and record what comes back —
verbatim. The assertion is over the **emitted bytes**, not over the config text.
In diff mode, repeat against the second revision and compare.

### Why a dead backend is not a weaker test — the key argument

This is what makes the whole approach valid without live upstreams, and it is
**service-agnostic**:

> The property under test is a rule the configuration declares
> **unconditionally**. That is exactly the class of rule that also survives on an
> **error response** — the server applies it regardless of what the upstream did,
> because it was told to apply it always. And an error response is **provably the
> worst case**: it is the path with the least upstream cooperation, the shortest
> processing, and the most opportunity for a rule to be skipped. A rule present
> on the error response is present on the success response a fortiori.

So measuring against a dead backend is **not** a weaker test than measuring
against a live one for unconditional rules — it is the stronger end of the same
test, obtained without any infrastructure.

### The single blind spot, declared

**A rule the configuration marks CONDITIONAL is not covered.** A directive that
applies only on certain statuses, only for certain content types, only when the
upstream set or omitted something, only on a matched response characteristic —
that rule may legitimately be absent from an error response, and the harness
cannot distinguish "correctly absent here" from "missing everywhere".

Declare this rather than glossing it. The harness should **enumerate the
conditional rules it found and state that they are out of scope**, in its own
output, next to the green. A gate that reports a clean run while silently not
covering a subset of the rules is the exact shape that turns into a false
assurance later; naming the subset costs one printed list and keeps the result
honest.

## 4. Portable vs blueprint

- **Blueprint (the whole page):** the rewrite table — which directives to
  neutralize, how to force foreground execution, where the binary insists on
  writing — is specific to each server binary and is the reason no portable
  script exists.
- **Durable across every implementation:** (a) render the **committed**
  configuration rather than a hand-written stand-in; (b) validate with the
  binary's own check mode before measuring; (c) sever upstreams to a dead local
  port and measure the server's own error responses; (d) assert over emitted
  bytes, never over config text; (e) the worst-case argument that makes (c)
  valid for unconditional rules; (f) declaring the conditional-rule blind spot in
  the output.

## 5. Pitfalls and sharp edges

- **Rewriting a directive that participates in the property under test
  invalidates the run.** Print the rewrite table every time so this is visible
  rather than assumed.
- **Static analysis of the configuration is the thing being replaced, not a
  sanity check on it.** When the two disagree, the emitted response is right.
  Resisting that is how a harness gets "corrected" back into a config parser.
- **A conditional rule read as covered is the one real false assurance here.**
  Enumerate them; do not let a green summary imply coverage the run does not
  have.
- **A dead port and a filtered port are not the same thing.** Nothing listening
  gives a prompt connection refusal and the server's own error path; a silently
  dropped connection gives a timeout path, which may be a different configuration
  branch with different emitted headers. Ensure the upstream port is genuinely
  refusing.
- **Scratch is not production.** The harness answers what the configuration
  emits; it does not answer whether the deployed instance is running that
  configuration. That is a separate check against the live endpoint.
- **The header matrix is the coverage.** A rule that only appears for certain
  request characteristics is only measured if the matrix contains them; an
  under-specified matrix produces a green with a silent gap.
- **Leaving the scratch server running poisons later runs.** Bind to a
  caller-chosen port, and tear down unconditionally, including on failure paths,
  so a second run does not measure the first run's process.

## 6. Tests that cover it

Cover: an unconditional rule present in the configuration appears in the emitted
error response for every route and header combination in the matrix; removing
that rule from the configuration makes the harness go red (the mutation that
proves it measures anything at all); a syntax error in the rendered tree fails at
the check step, before any request is sent; the upstream port genuinely refuses
connections; the rewrite table is printed and contains no directive involved in
an asserted rule; conditional rules are enumerated in the output and declared
out of scope; diff mode reports no difference between two identical revisions and
reports exactly the changed response fields between two that differ; the scratch
server is torn down even when a request fails.

## What it is
Spring's relational-persistence layer over JPA, with
[`hibernate-orm`](./hibernate-orm.md) as the usual provider beneath it. Entities
are annotated POJOs, and repositories are declared as interfaces whose
implementations Spring Data generates at runtime, removing most boilerplate DAO
code. Canonical coordinates:
`org.springframework.boot:spring-boot-starter-data-jpa`.

## Core API / usage shape
- **Entities**: classes annotated `@Entity` with an `@Id` field mapped to a
  table row.
- **Repositories**: interfaces extending `JpaRepository<T, ID>` (or a narrower
  Spring Data repository interface). Spring generates the implementation,
  providing CRUD operations plus derived query methods whose SQL/JPQL is
  inferred from the method name, and `@Query`-annotated methods for explicit
  queries.
- **Auditing**: an `AuditorAware<T>` bean plus the auditing configuration
  auto-populates created/modified metadata (and created-by/modified-by) on
  annotated entity fields.
- **`Persistable<ID>`**: an entity may implement it to control new-vs-existing
  detection explicitly via `isNew()`, overriding Spring Data's default
  heuristic.

## Idioms & best practices
- Let repositories be interfaces; use derived query methods for simple lookups
  and `@Query` for anything the method-name DSL cannot express clearly.
- Use `AuditorAware` and auditing annotations instead of hand-maintaining
  created/modified bookkeeping in application code.
- Implement `Persistable` when an entity's ID is assigned by the application
  rather than generated by the database, so Spring Data does not misinfer
  insert-vs-update from ID nullness.
- Own the schema with a versioned migration tool rather than letting the mapping
  shape it — see [`hibernate-orm.md`](./hibernate-orm.md), which owns the
  schema-authority rule and the `ddl-auto` settings that implement it.

## General pitfalls
- Default new-vs-existing detection assumes a null/absent ID means "new." An
  entity with a pre-assigned ID can therefore be treated as an update (and fail
  or no-op) — do not assume plain `save()` semantics once IDs are assigned
  outside the database; introduce `Persistable` to make the intent explicit.
- `Persistable` changes identity semantics for the repository, so adding it
  silently alters insert/update detection for that entity; verify the detection
  after the change. Overriding `equals`/`hashCode` has the same effect one layer
  down — see [`hibernate-orm.md`](./hibernate-orm.md).
- Lazy-loading and N+1 query patterns reach through the repository abstraction
  unchanged: a derived method returning a collection of parents will still fire
  one query per lazy child. These are provider-level traps, described in
  [`hibernate-orm.md`](./hibernate-orm.md); be deliberate about fetch strategy.
